## 1. Executive Summary — Why the Current App Fails

The current design has a basic technical problem:

1. **Android does not reliably expose RSSI for an already-connected Classic Bluetooth audio link (A2DP/HFP).**
   - `BluetoothLeScanner` only sees BLE advertising. Connected Classic headphones usually stop BLE advertising.
   - `BluetoothAdapter.startDiscovery()` is Classic inquiry. It is unreliable, slow, battery-heavy, interrupts audio, and usually will not give useful live RSSI for an already-connected headset.
   - `BluetoothGatt.readRemoteRssi()` only works for a GATT connection. Many headphones do not expose a usable GATT connection while acting as A2DP/HFP audio devices. If GATT cannot connect, there is no RSSI source.
   - Therefore the app cannot promise exact distance for every headset. The correct fix is: **probe for RSSI support, use it if available, otherwise show “proximity unavailable” and still provide connection-loss + last-known-location features.**

2. **The fixed RSSI-to-distance formula is not real distance.**
   - `txPower = -59`, `n = 2.2` is a guess. RSSI changes with body blocking, hand position, walls, head orientation, and headset firmware.
   - A 1 m threshold is especially unreliable without per-device calibration.
   - The app must show an **estimated range with confidence**, not “1.000 m”, and it must require calibration for small thresholds like 1 m.

3. **The 1 m alert probably never fires because:**
   - No usable RSSI source is actually arriving.
   - A single noisy RSSI sample is being filtered incorrectly or reset.
   - The device is not matched correctly.
   - The service is not receiving updates.
   - The alert logic uses distance but distance is stale/null.
   - There is no debounce/hysteresis.

4. **Disconnect detection is incomplete.**
   - `ACTION_ACL_DISCONNECTED` alone is not enough. Need A2DP/headset profile state broadcasts, profile proxy connected-device checks, and AudioManager output-device checks.
   - The app should mark disconnected, save last-known telemetry and location, and stop speaking after the headphones are gone.

5. **TTS may play on the phone speaker or sound harsh.**
   - Use `USAGE_MEDIA`, `CONTENT_TYPE_SPEECH`, `STREAM_MUSIC`, audio focus, and check that a Bluetooth media output exists before speaking.
   - Use polite, calm phrases. Do not say “Move back now!” or similar.

6. **Repeated scanning kills battery.**
   - Remove periodic `startDiscovery()`.
   - Do not run continuous BLE scans in production.
   - Use one GATT RSSI connection if supported, adaptive polling, and one-shot GPS only on disconnect.

## 4. Mandatory First Step: RSSI Capability Probe

The agent must not assume the headset supports GATT RSSI. Add a hidden or visible **Diagnostics → Test this headset** screen and run this probe before implementing alerts.

### Probe procedure

For the selected connected headset:

1. Read connected devices from:
   - `BluetoothA2dp.getConnectedDevices()`
   - `BluetoothHeadset.getConnectedDevices()`
   - `AudioManager.getDevices(AudioManager.GET_DEVICES_OUTPUTS)`

2. Try a single GATT connection:
   - `device.connectGatt(context, false, callback, TRANSPORT_AUTO)`
   - If that fails, optionally try `TRANSPORT_LE` or `TRANSPORT_BREDR` once each.
   - Wait up to 8 seconds.
   - On connected, call `gatt.readRemoteRssi()` 3–5 times with 1–2 s between reads.
   - Record: success count, RSSI values, GATT status, failure reason.

3. While connected, run a **limited** BLE scan for 5 seconds and look for the exact MAC address. If the device is not visible, do not keep scanning. Name matching is not reliable because names are duplicated and BLE addresses can rotate.

4. Run Classic discovery only from a manual diagnostics button, never continuously. Cap it at 10 seconds and stop it. Log whether the device appears. Do not use it as the production source.

### Result handling

| Probe result | App behavior |
|---|---|
| GATT RSSI works | Use GATT RSSI; display “RSSI source: GATT”; allow approximate distance after calibration |
| BLE scan sees same device | Use limited scan bursts; mark source as “BLE advertisement”; stop when not visible |
| No RSSI source | Set `ProximityState.UNAVAILABLE`; hide exact distance; keep disconnect detection + last location. Show “This headset does not expose signal strength to Android.” |
| Classic discovery only | Allow only for diagnostics/manual check; do not use for live alerts |

**Critical:** If no RSSI source exists, do not silently substitute a guessed distance. That is the primary bug.

## 6. Connected Device Detection — Replace Weak Logic

Create a single source of truth class, e.g. `ConnectionMonitor`. It must observe all of these:

1. `BluetoothManager.getAdapter()`
2. `BluetoothAdapter.getProfileProxy(...)` for `BluetoothProfile.A2DP`
3. `BluetoothAdapter.getProfileProxy(...)` for `BluetoothProfile.HEADSET`
4. `BluetoothA2dp.getConnectedDevices()`
5. `BluetoothHeadset.getConnectedDevices()`
6. `AudioManager.getDevices(AudioManager.GET_DEVICES_OUTPUTS)`
7. Broadcast receivers:
   - `BluetoothA2dp.ACTION_CONNECTION_STATE_CHANGED`
   - `BluetoothHeadset.ACTION_CONNECTION_STATE_CHANGED`
   - `BluetoothDevice.ACTION_ACL_CONNECTED`
   - `BluetoothDevice.ACTION_ACL_DISCONNECTED`
   - `BluetoothDevice.ACTION_ACL_DISCONNECT_REQUESTED`
   - `BluetoothAdapter.ACTION_STATE_CHANGED`
8. A low-frequency fallback poll every 10 seconds while monitoring.

### Data model

```kotlin
data class ConnectedAudioDevice(
    val name: String?,
    val address: String,
    val supportsA2dp: Boolean,
    val supportsHeadset: Boolean,
    val isCurrentAudioOutput: Boolean
)
```

### Important implementation rules

- Match by address, not name, whenever possible.
- A device name like `"WF-C500"` is not unique. Do not trust name-only matching.
- Do not call `BluetoothAdapter.startDiscovery()` every 3 seconds. Delete that loop from production.
- Do not call `getConnectedDevices(BluetoothProfile.GATT)` as the primary audio-device detector. It detects GATT connections, not A2DP/HFP audio connections.
- Close profile proxies in `onDestroy()` or equivalent.
- If the selected device disappears from all connected profiles/audio outputs, treat it as disconnected. Do not rely only on ACL broadcasts.
- Add a 5-second grace period to avoid false disconnects from profile glitches, but if it remains absent, record the disconnect.

## 7. RSSI Acquisition — Use Only What Actually Works

Create `RssiSourceManager`.

### Priority order

1. **GATT RSSI source** if the capability probe succeeds.
2. **Limited BLE scan bursts** only if the exact device is genuinely visible while connected.
3. **Manual diagnostic Classic discovery** only. Never production polling.

### GATT source skeleton

```kotlin
@SuppressLint("MissingPermission")
class GattRssiSource(
    private val context: Context,
    private val device: BluetoothDevice,
    private val onRssi: (Int) -> Unit,
    private val onUnavailable: (String) -> Unit
) {
    private var gatt: BluetoothGatt? = null
    private var reading = false
    private var failures = 0
    private val handler = Handler(Looper.getMainLooper())

    private val poll = object : Runnable {
        override fun run() {
            val g = gatt ?: return
            if (!reading) {
                reading = true
                if (!g.readRemoteRssi()) {
                    reading = false
                    onUnavailable("readRemoteRssi() returned false")
                }
            }
            handler.postDelayed(this, 2_000L)
        }
    }

    fun start() {
        try {
            gatt = if (Build.VERSION.SDK_INT >= Build.VERSION_CODES.M) {
                device.connectGatt(
                    context,
                    false,
                    callback,
                    BluetoothDevice.TRANSPORT_AUTO
                )
            } else {
                device.connectGatt(context, false, callback)
            }
        } catch (e: SecurityException) {
            onUnavailable("Missing BLUETOOTH_CONNECT")
        } catch (e: IllegalArgumentException) {
            onUnavailable("GATT unsupported for this device")
        }
    }

    private val callback = object : BluetoothGattCallback() {
        override fun onConnectionStateChange(
            gatt: BluetoothGatt,
            status: Int,
            newState: Int
        ) {
            if (newState == BluetoothProfile.STATE_CONNECTED) {
                failures = 0
                this@GattRssiSource.gatt = gatt
                handler.removeCallbacks(poll)
                handler.post(poll)
            } else {
                reading = false
                this@GattRssiSource.gatt?.close()
                this@GattRssiSource.gatt = null
                failures++
                onUnavailable("GATT disconnected, status=$status")
            }
        }

        override fun onReadRemoteRssi(
            gatt: BluetoothGatt,
            rssi: Int,
            status: Int
        ) {
            reading = false
            if (status == BluetoothGatt.GATT_SUCCESS && rssi in -110..-20) {
                onRssi(rssi)
            } else {
                failures++
                onUnavailable("RSSI failed: status=$status rssi=$rssi")
            }
        }
    }

    fun stop() {
        handler.removeCallbacksAndMessages(null)
        try {
            gatt?.disconnect()
            gatt?.close()
        } catch (_: Exception) {
        } finally {
            gatt = null
        }
    }
}
```

### Scheduler / battery rules

Use adaptive polling. Do not poll every 1 second forever.

| Situation | Poll interval |
|---|---|
| No RSSI source | No RSSI polling. Connection monitor only. |
| Safe, screen off | 8–12 s |
| Safe, screen on | 4–6 s |
| Within 1.5× warning threshold | 2–3 s |
| Moving-away trend detected | 2 s |
| LINK_RISK / IMMINENT | 1 s for a short window only |
| After disconnect | Stop RSSI immediately |

BLE scan fallback:
- Run only in a short burst: 3–5 seconds.
- Repeat no more than every 30–60 seconds.
- Stop fully after 3–5 consecutive no-result bursts.
- Never scan continuously.

Remove:
- periodic `startDiscovery()`
- continuous unfiltered BLE scan
- repeated GATT reconnects without exponential backoff
- location polling while safe

## 8. Signal Filtering, Calibration, and Distance

### 8.1 Filtering

Pipeline:

```
raw RSSI -> reject invalid -> moving median (5 samples) -> Kalman or EMA -> trend window
```

Kalman example:

```kotlin
private var estimate = 0.0
private var errorCov = 1.0
private val processNoise = 0.05
private val measurementNoise = 2.5

fun update(raw: Double): Double {
    errorCov += processNoise
    val gain = errorCov / (errorCov + measurementNoise)
    estimate += gain * (raw - estimate)
    errorCov = (1.0 - gain) * errorCov
    return estimate
}
```

Maintain:
- current raw RSSI
- filtered RSSI
- recent variance / standard deviation
- sample count
- last sample timestamp
- trend slope in dBm/sec
- source label

Do not alert on one sample. Require at least 5 valid samples and 2 seconds of sustained condition.

### 8.2 Per-device calibration

Store one model per device address:

```kotlin
data class CalibrationModel(
    val deviceAddress: String,
    val txPowerAtOneMeterDbm: Double,
    val pathLossExponent: Double,
    val calibrated: Boolean,
    val learnedDisconnectRssiDbm: Double? = null
)
```

Calibration wizard:
- Ask user to place phone and headphones at 1 m. Collect 20–30 RSSI samples over 10 s. Use the median.
- Ask user to place them at 3 m. Collect 20–30 samples. Use the median.
- Compute:

```kotlin
fun computeModel(
    rssiAt1m: Double,
    rssiAt3m: Double,
    d2Meters: Double = 3.0
): Pair<Double, Double> {
    val n = (rssiAt1m - rssiAt3m) /
        (10.0 * log10(d2Meters))
    val clampedN = n.coerceIn(1.2, 4.5)
    return rssiAt1m to clampedN
}
```

- If the user only calibrates one point, keep `n = 2.0` and clearly mark confidence as low.
- If no calibration exists, compute distance only for display as “rough” and do not promise sub-2 m accuracy. For the 1 m threshold, prompt: “Calibrate before using 1 m alerts.”

Distance formula:

```kotlin
fun rssiToMeters(
    rssiDbm: Double,
    txPowerAtOneMeterDbm: Double,
    pathLossExponent: Double
): Double = 10.0.pow(
    (txPowerAtOneMeterDbm - rssiDbm) /
    (10.0 * pathLossExponent)
)
```

Confidence range:

```kotlin
val sigma = sqrt(rssiVariance)
val lowerMeters = rssiToMeters(filteredRssi + sigma, tx, n)
val upperMeters = rssiToMeters(filteredRssi - sigma, tx, n)
```

Show:
- `~1.2 m (likely 0.8–2.0 m, low confidence)`
- Do not show `1.000 m`.
- If `sigma` is high or samples are few: `Confidence: LOW`.
- If no source: `Distance unavailable for this headset`.

### 8.3 Trend detection

Maintain a sliding window of timestamped filtered RSSI values.

Use linear regression over the last 8–10 seconds with at least 5 samples:

```kotlin
fun slopeDbmPerSecond(samples: List<TimedRssi>): Double? {
    if (samples.size < 5) return null
    val t0 = samples.first().timeMs
    val xs = samples.map { (it.timeMs - t0) / 1000.0 }
    val ys = samples.map { it.rssi }
    if (xs.last() - xs.first() < 3.0) return null
    val xMean = xs.average()
    val yMean = ys.average()
    val numerator = xs.indices.sumOf { (xs[it] - xMean) * (ys[it] - yMean) }
    val denominator = xs.indices.sumOf { (xs[it] - xMean) * (xs[it] - xMean) }
    if (denominator == 0.0) return null
    return numerator / denominator
}
```

Negative slope means signal is getting weaker, i.e. moving away.

Do not use “4 dBm drop in 3 s” as the only rule. It is noisy and can misfire.

## 9. Alert Engine — Polite, Debounced, Confidence-Aware

### States

```kotlin
enum class ProximityState {
    UNAVAILABLE,
    SAFE,
    MOVING_AWAY,
    AT_LIMIT,
    LINK_RISK,
    IMMINENT,
    DISCONNECTED
}
```

### Decision logic

```text
If no RSSI source or stale sample (> 8 s)
    -> UNAVAILABLE

If device disconnected
    -> DISCONNECTED

If filteredRssi <= disconnectThreshold + 2 dBm
    -> IMMINENT

Else if predictedSecondsToLoss != null && predictedSecondsToLoss <= 7 s
    -> IMMINENT

Else if predictedSecondsToLoss != null && predictedSecondsToLoss <= 20 s
    -> LINK_RISK

Else if distance >= warningDistance
    OR (distance >= warningDistance * 0.8 AND slope < -1.0 dBm/s)
    -> AT_LIMIT

Else if slope < -1.0 dBm/s for at least 2 s
    -> MOVING_AWAY

Else
    -> SAFE
```

### Hysteresis and debounce

- Enter warning when `distance >= threshold`.
- Exit warning only when `distance <= threshold * 0.85`.
- Require the candidate condition to remain true for 2 seconds before changing to `AT_LIMIT` or `LINK_RISK`.
- Require 1 second for `IMMINENT`.
- Cooldown TTS per state:
  - `MOVING_AWAY`: 45 s
  - `AT_LIMIT`: 30 s
  - `LINK_RISK`: 20 s
  - `IMMINENT`: 10 s
- Never repeat the same sentence on every sample.
- Escalation should speak once, then stay silent until state changes or cooldown expires.

### Predicting imminent disconnection

Use a learned disconnect RSSI threshold if available. When a disconnect occurs, store the last filtered RSSI for that device. Use the average of the last few disconnects, clamped to a safe range such as `-95..-70 dBm`.

Formula:

```kotlin
fun secondsToLoss(
    filteredRssi: Double,
    slopeDbmPerSecond: Double?,
    lossThresholdDbm: Double
): Double? {
    if (slopeDbmPerSecond == null || slopeDbmPerSecond >= -0.2) return null
    val margin = filteredRssi - lossThresholdDbm
    if (margin <= 0.0) return 0.0
    return margin / (-slopeDbmPerSecond)
}
```

Display:
- “Connection risk: possible loss in ~12 s”
- “Stream quality is dropping”
- Never say “will disconnect in exactly 12 s”.

If no RSSI is available, do not display prediction. Only notify after disconnection.

## 11. Disconnect Detection and GPS Last-Location

### 11.1 Disconnect detection

Treat the device as disconnected only when all reliable checks agree:

1. It is absent from `BluetoothA2dp.connectedDevices`
2. It is absent from `BluetoothHeadset.connectedDevices`
3. It is absent from `AudioManager.getDevices(...)`
4. ACL disconnected broadcast received, or profile state is `STATE_DISCONNECTED`
5. It remains absent for a short grace period, e.g. 3–5 seconds

If it reconnects within the grace period, do not save a disconnect event.

On confirmed disconnect:
- Stop RSSI source immediately.
- Stop TTS, release audio focus.
- Do not say “move closer” through the phone speaker.
- Save the last known telemetry:
  - timestamp
  - device name/address
  - last raw RSSI
  - last filtered RSSI
  - last estimated distance/range
  - last source
  - last state
- Capture one-shot location, best effort.
- Post a notification with:
  - “Headphones disconnected”
  - “Last known location saved at 10:42”
  - Action: “Open last location”
- If no location permission: “Location unavailable. Enable location permission to save disconnect location.”

### 11.2 Location capture

Do not track location continuously. Do this once per disconnect, with a timeout.

```kotlin
data class DisconnectEvent(
    val timestampMs: Long,
    val deviceName: String?,
    val deviceAddress: String,
    val lastRssi: Int?,
    val lastDistanceMeters: Double?,
    val latitude: Double?,
    val longitude: Double?,
    val accuracyMeters: Float?
)
```

Implementation requirements:
- Request `ACCESS_FINE_LOCATION` and `ACCESS_COARSE_LOCATION` at runtime.
- `ACCESS_BACKGROUND_LOCATION` only if the user enables background last-location saving. Do not request it with the initial permission dialog.
- Use `LocationManager` from the Android framework. Do not add Google Location dependency.
- First try `getLastKnownLocation()` from GPS, network, and passive providers.
- If last-known is older than 2 minutes, request one current fix with `requestSingleUpdate` or `getCurrentLocation`, timeout after 5–7 seconds, then fall back to the last known location.
- Catch `SecurityException`.
- If no location can be obtained, save the event with `latitude = null` and `longitude = null`.
- Store at most 20 recent events in `SharedPreferences` as JSON. Do not add Room unless it already exists.
- Add a “Clear history” button in the UI.
- Open map using:

```kotlin
val uri = Uri.parse("geo:$lat,$lon?q=$lat,$lon($label)")
context.startActivity(Intent(Intent.ACTION_VIEW, uri))
```

- Do not upload locations anywhere.
- Show a privacy explanation before requesting background location.

### 11.3 Notification

Create separate channels:

- `monitoring` — low importance, ongoing foreground service notification.
- `alerts` — high importance for imminent warnings.
- `disconnect_location` — default importance, one notification per saved disconnect.

Do not use one noisy channel for everything.

## 13. Battery-Saving Rules

Use these rules and remove the old behavior:

- Remove periodic `BluetoothAdapter.startDiscovery()` entirely from production.
- Remove continuous `BluetoothLeScanner.startScan()`.
- Use one GATT connection per selected device only if the probe proves it works.
- Use adaptive RSSI polling intervals.
- Stop RSSI polling immediately on disconnect.
- Stop TTS processing when not in a warning state.
- Do not hold a wakelock. The foreground service and Handler are enough.
- Do not poll GPS continuously. Capture location only on disconnect.
- Do not poll connected devices every second. Use broadcasts plus a 10 s fallback poll.
- Do not run both BLE scan and GATT polling at the same time unless the probe explicitly requires fallback.
- Add a Battery Saver mode that increases intervals and disables voice for low-severity states.

## 16. What NOT To Do

- Do not keep `startDiscovery()` every 3 seconds.
- Do not run continuous BLE scans while connected.
- Do not assume name matching is enough.
- Do not show exact meters from an uncalibrated RSSI formula.
- Do not display `0.1 m` precision.
- Do not speak warnings on the phone speaker after headset disconnect unless explicitly enabled.
- Do not reset last-known distance/location to null and lose the disconnect evidence.
- Do not call `connectGatt()` repeatedly without closing previous GATT instances.
- Do not add Gradle dependencies.
- Do not block the main thread with Bluetooth polling.
- Do not request continuous GPS for battery-heavy proximity monitoring.
- Do not claim the app can predict exact disconnection time.
- Do not hide the “RSSI unavailable” state from the user.

---

## 17. The Final Important Decision

If your goal is **“warn me when my headphones are exactly 1 m away”**, the realistic Android solution is:

1. The headset must expose usable GATT RSSI to Android, or BLE advertising must still be visible while connected.
2. The app must be calibrated at 1 m and 3 m.
3. The app must show a range and confidence, not a precise number.
4. The alert must use debounce and trend detection.

If the headset does **not** expose RSSI, no code can make exact Bluetooth distance work with standard Android public APIs. The honest fallback is:

- Detect connection loss.
- Save last-known GPS location.
- Notify the user immediately.
- Show that pre-disconnect proximity alerts are unavailable for that headset.

That is the correct, finished behavior. Any implementation that claims otherwise is guessing.
